## 一、修复概述

本次修复针对 **BootLoader_dualBank** 及 **App_dualBank** 进行系统性审查，共修复 **15 项问题**（BootLoader 14 项 + App 端 1 项关键配置），覆盖 **P0（致命）3 项、P1（严重）3 项、P2（中等）8 项**。所有修改旨在使 Bootloader 烧写 App 以及 App 安全访问后跳转 Bootloader 的机制符合车企标准流程。

#### P0-1: `uds_alg.c` — `index` 变量未声明导致编译失败

| 项目 | 内容 |
|:---|:---|
| **问题描述** | `UDS_ALG_HAL_GetRandom()` 函数中使用了未声明的变量 `index`，导致编译器报错，无法生成目标文件。 |
| **风险等级** | 🔴 致命 — 编译阻断 |

#### P0-2: `uds_app.c` — `BANK_VALID_MAGIC` 与 CRC32 存储值不匹配，导致 Active Bank 覆盖保护失效

| 项目 | 内容 |
|:---|:---|
| **问题描述** | `RequestDownload0x34()` 中检查目标 Bank 是否有效时，使用 `bankA_valid == BANK_VALID_MAGIC`（魔数 `0x55AA55AA`）进行判断。但 `Boot_DualBank.c` 中 `MarkBankValid()` 实际存入的是 **CRC32 值**，不是固定魔数。因此 `targetBankValid` 永远为 `FALSE`，禁止覆盖 Active Bank 的保护逻辑实际上**完全未生效**。 |
| **风险等级** | 🔴 致命 — 可在运行中直接覆盖当前有效固件，导致 ECU 变砖 |
| **影响范围** | BootLoader + App（两边 `uds_app.c` 均存在） |
| **修复位置** | `uds_app.c` 第 1301 / 1305 行 |
| **修复内容** | 将 `== BANK_VALID_MAGIC` 改为 `!= 0u`，与 `Boot_DualBank_VerifyBank()` 的语义保持一致（非零即表示已标记为有效）。 |
| **修复前** | `targetBankValid = (flags.main.bankA_valid == BANK_VALID_MAGIC);` |
| **修复后** | `targetBankValid = (flags.main.bankA_valid != 0u);` |

---

#### P0-3: `uds_app.c` — `CheckProgrammingConditions()` 存在严重逻辑错误

| 项目 | 内容 |
|:---|:---|
| **问题描述** | 该函数存在两处严重缺陷：<br>1. 无条件调用 `Boot_DualBank_SetTargetWriteBank(BANK_A)`，会**覆盖 `0x34` 根据下载地址自动判断的目标 Bank**，导致刷写到错误的 Bank；<br>2. 使用未初始化的局部变量 `targetBank`（`uint8 targetBank;` 后直接 `if (targetBank == BANK_B)`），行为未定义。 |
| **风险等级** | 🔴 致命 — 刷写目标 Bank 错误，升级后启动的是旧版本或空 Bank |
| **影响范围** | BootLoader + App（两边 `uds_app.c` 均存在） |
| **修复位置** | `uds_app.c` 第 1461–1494 行 |
| **修复内容** | 移除强制设置 BANK_A 的代码，改为直接读取当前 `targetWriteBank` 并返回对应的状态码。 |
| **修复前** | `Boot_DualBank_SetTargetWriteBank(BANK_A);`<br>`if (targetBank == BANK_B) { ... }` |
| **修复后** | `uint32 targetWriteBank = Boot_DualBank_GetTargetWriteBank();`<br>`if (targetWriteBank == BANK_B) targetBankChar = 0x0B; else targetBankChar = 0x0A;` |

### 🟠 P1 — 严重问题（3 项）

---

#### P1-4: `uds_app.c` — S3 超时后不会自动回退到 Default Session

| 项目 | 内容 |
|:---|:---|
| **问题描述** | `UDS_SystemTickCtl()` 虽然递减了 `xUdsS3ServerTime`，但**没有任何地方调用 `IsS3ServerTimeout()`** 来执行会话回退。这意味着如果诊断仪在 Extended/Programming Session 下断开，ECU 将**永远停留在非默认会话**，Security Level 也不会重置，存在安全风险。 |
| **风险等级** | 🟠 严重 — 违反 UDS 标准，会话和安全状态滞留 |
| **影响范围** | BootLoader + App（两边 `uds_app.c` 均存在） |
| **修复位置** | `uds_app.c` 第 375–386 行（`UDS_SystemTickCtl()`） |
| **修复内容** | 在定时器控制函数末尾添加 S3 超时检测及会话回退逻辑。 |
| **修复后** | ```c<br>if ((0u == GetUdsS3ServerTime()) && (TRUE != IsCurDefaultSession()))<br>{<br>    SetCurrentSession(DEFALUT_SESSION);<br>    SetSecurityLevel(NONE_SECURITY);<br>    Flash_InitDowloadInfo();<br>    Flash_SetNextDownloadStep(FL_REQUEST_STEP);<br>}<br>``` |
| **车企标准要求** | ISO 14229 规定：S3Server 超时后必须自动回到 Default Session 并重置 Security Level。 |

---

#### P1-5: `uds_app.c` — 安全访问无尝试次数限制和锁定机制

| 项目 | 内容 |
|:---|:---|
| **问题描述** | `SecurityAccess0x27()` 中没有检查连续失败次数，也没有启动锁定计时。诊断仪可以无限次尝试 Key，存在暴力破解 Seed/Key 的安全隐患。虽然 `xSecurityReqLockTime` 变量存在，但从未在收到 `0x27` 请求时进行检查。 |
| **风险等级** | 🟠 严重 — 安全访问可被暴力破解 |
| **影响范围** | BootLoader + App（两边 `uds_app.c` 均存在） |
| **修复位置** | `uds_app.c` 第 918–1058 行（`SecurityAccess0x27()`） |
| **修复内容** | 1. 函数开头增加锁定时间检查：若 `xSecurityReqLockTime > 0`，返回 `NRC_REQUIRED_TIME_DELAY_NOT_EXPIRED`（0x37）；<br>2. 增加静态失败计数器 `s_securityAttemptCnt`（上限 3 次）；<br>3. 连续失败 3 次后启动 10 秒锁定，返回 `NRC_EXCEEDED_NUMBER_OF_ATTEMPTS`（0x36）；<br>4. 解锁成功后清零计数器。 |
| **车企标准要求** | ISO 14229 / 主流 OEM 规范：连续 Key 验证失败达到上限后应锁定一段时间。 |

---

#### P1-6: `uds_app.c` — `0x36` TransferData 未验证序列号（SN）

| 项目 | 内容 |
|:---|:---|
| **问题描述** | `TransferData0x36()` 中仅执行了 `gs_RxBlockNum++`，但**没有校验接收到的序列号** `m_pstPDUMsg->aDataBuf[1]` 是否与预期值一致。UDS 标准明确要求检查 SN，不匹配时应返回 `NRC_REQUEST_SEQUENCE_ERROR`。 |
| **风险等级** | 🟠 严重 — 数据帧乱序不会被检测，可能导致 Flash 写入错误数据 |
| **影响范围** | BootLoader + App（两边 `uds_app.c` 均存在） |
| **修复位置** | `uds_app.c` 第 1363–1427 行（`TransferData0x36()`） |
| **修复内容** | 在 `gs_RxBlockNum++` 之前添加 SN 校验：若 `rxSN != gs_RxBlockNum`，返回 `NRC_REQUEST_SEQUENCE_ERROR`（0x24），并重置下载状态机。 |

## 四、车企标准刷写流程验证

```
┌─────────────────────────────────────────────────────────────────────┐
│                     标准车企刷写流程 (ISO 14229)                      │
├─────────────────────────────────────────────────────────────────────┤
│  APP 端：请求进入 Bootloader                                          │
│    1. 诊断仪 → APP: 0x10 03  Extended Session                         │
│    2. 诊断仪 → APP: 0x27 01/02 SecurityAccess Level 1  ← 尝试限制已修复│
│    3. 诊断仪 → APP: 0x10 02  Programming Session                      │
│       → APP 设置 RAM_BOOT_MODE_APP + 正响应后 SW_Reset()              │
│       → ⚠️ 此逻辑仅在 DIAGNOSTIC_MODE_FOR_APP 下编译（P2-14 已修复）  │
├─────────────────────────────────────────────────────────────────────┤
│  Bootloader 端：主编程流程                                            │
│    4. Bootloader 检测到 RAM 标志 → 留在 Bootloader 模式               │
│    5. 诊断仪 → BL: 0x27 03/04 SecurityAccess Level 2  ← 尝试限制已修复 │
│    6. 诊断仪 → BL: 0x31 01 FF00 EraseMemory  ← 需要 Security Level 2  │
│    7. 诊断仪 → BL: 0x34 RequestDownload  ← Active Bank保护已修复(P0-2)│
│    8. 诊断仪 → BL: 0x36 TransferData  ← SN校验已添加 (P1-6)          │
│    9. 诊断仪 → BL: 0x37 RequestTransferExit                           │
│   10. 诊断仪 → BL: 0x31 01 DFFF CheckProgrammingDependency (CRC+激活)  │
│   11. 诊断仪 → BL: 0x11 03  Soft Reset  ← Tx回调后复位已修复 (P2-9)   │
├─────────────────────────────────────────────────────────────────────┤
│  会话超时保护                                                          │
│   • S3 超时 10 秒无通信 → 自动回退 Default Session + 重置安全级别      │
│     ← P1-4 已修复（BootLoader + App 均生效）                          │
└─────────────────────────────────────────────────────────────────────┘
```

## 六、后续建议

1. **硬件验证**：建议在真实 TC234 目标板上进行完整的端到端刷写测试：
   - APP 中发送 `0x10 02` 验证是否能正确复位进入 Bootloader
   - Bootloader 中验证 Bank 切换、CRC 校验、复位跳转
2. **OEM 适配**：不同车企对 RID（如 `0xDFFF` / `0xFF01`）、DID（如 `F184` BootSoftwareFingerprint）的定义可能不同，需根据具体 OEM 规范进一步调整。
3. **Seed 随机性**：当前 Seed 已引入 CPU 频率、复位状态、LCG 迭代等熵源，如有更高安全要求，建议集成硬件 TRNG。
4. **版本管理**：建议将本次修复后的代码作为新的基线版本，并更新 Bootloader 版本号。

## 七、回滚机制修复（追加修复）

### 7.1 修复概述

应用户要求，对双 Bank 刷写失败回滚机制进行深度审查，发现并修复 **3 项 P0/P1 级缺陷**。

| 缺陷 | 级别 | 文件 | 修复内容 |
|:---|:---|:---|:---|
| `bootAttempts` 机制未实现 | **P0 致命** | `Boot_DualBank.c` | 补充递增逻辑 + `MAX_BOOT_ATTEMPTS` 超限后自动回退到 fallback Bank |
| Flash 驱动错误静默 | **P0 致命** | `Flash.c` | `Flash_erasePFlash_port` / `Flash_writePFlash_port` / `Flash_writePFlash_portex` 操作后检查 `FLASH0_FSR` 错误位，失败时返回非 0 |
| 允许覆盖 active bank | **P1 高风险** | `uds_app.c` | 删除 "valid=0 时允许覆盖 active bank" 的逻辑，改为**一律禁止**向 active bank 下载 |

### 7.3 关键代码变更

#### (1) bootAttempts 递增 + 超限回退

```c
/* Boot_DualBank_SelectAndJump() */
if (targetStatus == BANK_STATUS_VALID)
{
    flags.main.bootAttempts++;
    flags.main.sequence++;
    Boot_DualBank_WriteFlags(&flags);

    if (flags.main.bootAttempts >= MAX_BOOT_ATTEMPTS)
    {
        Boot_DualBank_InvalidateBank(targetBank);
        fallbackStatus = Boot_DualBank_VerifyBank(fallbackBank);
        if (fallbackStatus == BANK_STATUS_VALID)
        {
            flags.main.activeBank = fallbackBank;
            flags.main.bootAttempts = 0u;
            flags.main.sequence++;
            Boot_DualBank_WriteFlags(&flags);
            SW_Reset();
        }
        else
        {
            return;  /* Both invalid -> stay in bootloader */
        }
    }
    else
    {
        Boot_DualBank_JumpToBank(targetBank);
        return;
    }
}
```

**行为：**
- 每次 Bootloader 尝试跳转到 active Bank 前，`bootAttempts` 先 +1 并写入 DFlash
- 如果 APP 成功启动，会在早期调用 `Boot_DualBank_ClearBootAttempts()` 清零
- 如果 APP 崩溃（Trap / WDT）未到达清零点，下次复位 `bootAttempts` 继续累积
- 连续 **3 次**（`MAX_BOOT_ATTEMPTS`）失败后，自动 invalidate 该 Bank 并切换到 fallback Bank

#### (2) Flash 硬件错误检查

```c
/* Flash_erasePFlash_port() */
if (FLASH0_FSR.B.EVER || FLASH0_FSR.B.OPER || FLASH0_FSR.B.SQER || FLASH0_FSR.B.PROER)
{
    return -1;  /* Erase error detected */
}

/* Flash_writePFlash_port() / Flash_writePFlash_portex() */
if (FLASH0_FSR.B.PVER || FLASH0_FSR.B.OPER || FLASH0_FSR.B.SQER || FLASH0_FSR.B.PROER)
{
    return -1 / 0;  /* Write error detected */
}
```

**检测的错误类型：**
- `EVER` — Erase Verify Error（擦除验证失败）
- `PVER` — Program Verify Error（编程验证失败）
- `OPER` — Flash Operation Error（通用操作错误）
- `SQER` — Command Sequence Error（命令序列错误）
- `PROER` — Protection Error（访问保护错误）

#### (3) 禁止向 active bank 下载

```c
if (Boot_DualBank_GetTargetWriteBank() == Boot_DualBank_GetActiveBank())
{
    /* Never allow flashing the active bank, even if it appears invalid.
     * The dual-bank design always writes to the INACTIVE bank first,
     * then switches. */
    SetNegativeErroCode(..., NRC_CONDITIONS_NOT_CORRECT, ...);
    Ret = FALSE;
}
```
